# Test Style

Conventions for the test suite: which tier a test belongs to, what each tier may touch, where a test lives, and the one rule that keeps the suite separable. `docs/DOCSTYLE.md` covers prose; this covers tests. `README.md`'s Quality Gates section says which invocations run at which stage, and is not repeated here.

## Three tiers

Every test is one of three, and the tier decides both what the test may depend on and how it is selected.

- **Unit**: asserts one module's own contract, imports that module by its own path, and touches no filesystem beyond `tmp_path`, no `data/`, no network, no Docker and no other module's behaviour except through stubs. Untagged; this is the default tier and the one the fast invocation runs.
- **Integration**: exercises a stage across several modules with synthetic fixtures, proving they are wired together correctly. Tagged `@pytest.mark.integration`, and opted out of for fast iteration. One end-to-end path per stage is the target shape, not one per feature. Breadth and cost both have to be present: the tag exists so a slow test can be skipped, so a test that reaches many modules and still runs in milliseconds is not tagged, because excluding it buys nothing. `company_cleanse` is the measured case, its composed entry points reaching eight to ten modules against one- and two-row in-memory frames, in the same hundredth-of-a-second band as the narrow tests beside them.
- **Acceptance**: a run against real `data/`, proving a mechanism improves something at scale. Never a test in the suite: it is a command line named in a handoff and run by a person, and its result is recorded with the work it measures.

`performance` is the existing opt-in marker for long-running benchmarks and is orthogonal to the tiers: a benchmark can be a unit or an integration test that also happens to be slow.

`graphics` is the third orthogonal marker: a test that renders a picture to disk through the plotting library, whether it calls a render function directly or drives a pipeline with rendering on. The render is what the test costs, and a test asserting a rendered image asserts the plotting library, not the code under test, so the fast invocation leaves them out. The better shape is a render switch on the producing function so only the tests that genuinely check a file on disk pay for it, and an assertion on the data at the site instead of the file; where a path has that switch, a test that does not read the picture passes it off rather than carrying this marker.

### Selecting the unit tier

The fast invocation (`pytest -m "not integration and not performance and not graphics"`) only deselects what carries one of those two markers, and almost nothing did: a test's tier was effectively decided by whether someone remembered to tag it, which is not a rule. `tooling/test_tier_classifier.py` states what a broad test does instead: it starts a subprocess (`subprocess.run`/`Popen`/`call`/`check_call`/`check_output`), materialises a layer (calls a `materialize_<something>` function or `swap_layer_into_place`, the repo's naming convention for the functions that publish a layer for real), or reads a corpus (computes a repo-root path via `Path(__file__).resolve().parents[N]` together with a `"data"` path segment, as opposed to a synthetic `tmp_path / "data" / ...` fixture that only mirrors the production layout) -- checking a test's own source and the source of every fixture it depends on, transitively, since the behaviour usually lives in a fixture rather than the test body.

The rule is not a runtime hook: a collection-time hook that reclassifies matching tests silently on every run leaves no reviewable artefact, the wrong trade for a population of a few dozen static annotations. The rule has two static halves instead, the shape this repo already uses for `check_direct_tests.py` and `check_layer_path_literals.py`:

- The 39 tests the classifier found that day are real `@pytest.mark.integration` decorators, applied by hand to their own test files -- a reviewable diff, not a hook nobody can see the effect of.
- `tooling/check_test_tier_markers.py` is the ratchet that keeps them honest: it runs a real `pytest --collect-only` pass with itself registered as the collection plugin (fixture resolution, including `conftest.py` inheritance and parametrisation, is pytest's own machinery and not worth re-deriving statically), reports every test that matches a signature but carries no marker, and `src/tests/baselines/test_tier_markers.txt` -- empty at the rule's introduction -- fails the gate on a new one. Run it directly for the same list a human can read: `pytest --collect-only -q -p check_test_tier_markers`, or `uv run --no-sync python tooling/check_test_tier_markers.py`.

The check is by behaviour, not by path or file location, so a marker survives a test file moving between directories. It is also shallow by design: it reads source rather than running the test, follows one level of same-module helper indirection, and cannot see behaviour reached only through a mocked collaborator or a deeper call chain. A test that needs excluding for a reason the classifier cannot see still needs its own `@pytest.mark.integration` or `@pytest.mark.performance`, same as before.

Measured on this rule, the unit selection keeps about 96% of the suite's tests for a little over half its wall time, a real but modest move on both axes, because the rule only reclassifies what a test's own source and its fixtures' source actually say it does. The counts and timings it was measured at are not repeated here, since a suite total copied into a reference doc is wrong from the next landing onwards; a fresh `pytest --durations=0` is the current figure.

A test that records a known defect rather than asserting correct behaviour is marked `@pytest.mark.xfail` with `strict=True`, the exception it expects, and a reason naming the item that will remove it. Strict is what makes such a marker self-clearing: without it a fix turns the test into a silent pass and the marker survives the thing it described, so the next reader meets a test that looks aspirational when it is in fact the only reason a green suite sits over live-broken behaviour. `pytest.ini` sets no `xfail_strict` default, so the flag is per-marker and leaving it off gives the unsafe form.

Scope a survey's coverage run to one area because it is faster and easier to read, not because a wider one breaks. A full-suite context-tracking run over the whole monorepo completes in about six minutes: measured at 6,054 passed and 8 skipped, after an unscoped command was run by accident. Earlier tagging items claimed such a run had been found to hang; no measurement was ever recorded for that claim, and the one measurement since contradicts it. Treat a slow run as slow.

Coverage fan-out is the usual way to find breadth, and it fails in both directions, so treat a count as a lead rather than a verdict. It over-counts when a test reaches shared plumbing every caller touches, or reaches a collaborator only through a mock: neither is exercised. It under-counts when the work happens outside the run's scope, since an area-scoped `--cov` sees only what happens inside that area, so a lazily imported call into another package is real breadth the number cannot show. A low count is therefore not proof of narrowness. Confirm each candidate by reading it and saying why it is broad or slow; across the areas surveyed so far it is the reading, not the count, that settled every ambiguous case.

An area with nothing to tag is a finding, not a failed survey. Reporting zero, with the fan-out and duration spreads that establish it, is a complete result; four areas surveyed this way produced four different relationships between those two numbers, so no area's outcome predicts the next one's. The pressure to tag something because other areas did is worth naming, because a marginal tag backed by a real fan-out number survives review in a way a plain guess would not, and it costs the marker its meaning: once tests are tagged that cost nothing to run, the fast invocation no longer tells anyone what it excluded.

## The direct-test rule

Every module that defines a function or class has a direct test: a test file in the module's own test root (the placement rule below: `src/tests/<area>/` for an area module, `packages/<package>/tests/` for a package module) that imports the module by its own path, or imports from its package a name the package's `__init__` re-exports from that module. An import from another area's tests is a caller's coverage however direct the import, since that test is asserting its own area's behaviour and using the module as a tool. Coverage reached only through a caller does not count, however high it is: a stage-level test proves the system as wired together works today, not that the module's own decision rule is asserted anywhere. `layer_layout.py` reached 98% line coverage this way with nothing checking its resolver's rules directly, which is the failure this rule exists to prevent.

The rule binds at the moment a module's contract is added or changed: the change ships with its direct test. It does not demand a test for every line; a thin pass-through with no independent logic needs none, a new or changed branching rule does.

`tooling/check_direct_tests.py` lists the modules that have no direct test, and `src/tests/baselines/direct_tests.txt` is that list as a baseline, one module per line, which `src/tests/tooling/scripts/test_direct_tests.py` holds the repo to. A module beyond the list fails the test: a new module shipped with nothing asserting its contract, and the fix is the test, never a new line; a change to the measurement itself re-baselines in the same commit, naming the lines it added and why. A module that gains a direct test leaves a stale line, which the test warns about. Working directly, delete the line in the same commit. In a dispatched stream, report the lines your tests cleared and leave the file alone: the lander deletes them at landing from a fresh run on the rebased branch, the one actor that sees the change against every stream already landed. A wrong deletion would be caught either way, since the module then reads as beyond the baseline and fails, so this is a division of labour rather than a safety net. What reporting buys is that a stream says why a line cleared instead of silently removing it, and twice already that reason has been the finding: one module that turned out not to be a module at all, and three that already had direct tests through a lazy re-export the checker could not see.

## Where a test lives and what it is called

- An area's tests live in `src/tests/<area>/`, a package's in `packages/<package>/tests/`. A test for a script lives in `src/tests/<area>/scripts/`, under the area owning the entry point that script runs, so the path states the owner rather than leaving it to be re-derived. The tests of the repo gate and shared tooling scripts, and any test whose subject is consistency across several areas' scripts, live in `src/tests/tooling/scripts/` instead: `tooling/` is an area, and those scripts drive no other one.
- A direct test is named for its module: `test_<module>.py`, with `test_<module>_<aspect>.py` when one file would grow past reading. The name is a convention for finding it; the import is what makes it direct.
- A test that spans areas by construction, a stage handoff or a pipeline path, lives with the area that owns the entry point it drives, tagged integration.

## Script tests and the shallow dry run

A script test asserts that the script resolves its arguments, picks the right inputs, and reaches the call it exists to make: the entry point's own contract. It does not need to run the work behind that call to prove this, and when it does anyway just to reach that assertion, it pays the real work's cost for something that stops well before it. The work's own correctness is a different assertion and belongs to a direct test of the module that does it, not to the script that dispatches to it.

Where a script supports it, prove wiring with `--dry-run` (`scripts/cli_common.add_dry_run_arg`/`report_dry_run`) instead of a real invocation: call the script with `--dry-run`, assert on the reported plan, and assert nothing was written. The dry run is shallow by design: it resolves arguments, reports what it would do, and stops immediately before the call; no flag threads down into the module doing the real work, and nothing below the entry point learns it is in a dry run. A script opts in by adding the flag through the shared helper and checking it once, at its own entry point.

This is now a per-area sweep rather than a convention stated once: each area carries an item to convert its own script tests, and each waits on the item that settles which tier a converted test is selected into, because a conversion measured against today's selection is measured against a tier that does not yet exist. What has not changed is the judgement inside a single conversion: a script test that already proves wiring cheaply (through mocking a collaborator, or by calling a resolver function directly rather than through the CLI) needs no change, and a test whose assertion is really about the work's output rather than the entry point's wiring is kept and marked as the broader tier it belongs to, not converted. Where a script's tests live is a separate question, answered per area by `Where a test lives and what it is called` above.

## Broad tests, and retiring them

A broad test is not wrong, it is expensive: it is the only coverage some modules have, so nothing under it can be reshaped without it breaking, and it cannot be skipped without losing that coverage. The order of work is therefore fixed. First give each module under it a direct test. Then measure what the broad test covers that no direct test does. If nothing, cut it to one end-to-end path for its stage and tag it integration; if something, that something is a missing direct test, so write that first. Retire by that evidence, never by reading.

Duplicate cases inflate a suite without protecting anything: two tests that build the same fixture and assert the same outcome through different callers are one test. `pyscn`'s clone detection over a tests directory finds them.

## Fixtures and data

- Build fixtures synthetically and small, under `tmp_path`. A test never reads or writes `data/`: it is shared physical storage across every worktree and session, and a fixture built there is a collision waiting to happen.
- A fixture that has to be large to mean anything is an acceptance run, not a test.
- Do not mock the module under test's own collaborators to make a unit test pass when the real collaborator is cheap; mock what is slow, external or non-deterministic.

## Running

The two suite invocations, full and fast, are documented in `README.md`'s Quality Gates section. The cheapest check during iteration is the area's own test directory; it is not a substitute for the full run the lander performs before merging.
